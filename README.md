# AstaLyaVistaService

API системы ведения задач: FastAPI, SQLAlchemy и PostgreSQL.

## Сборка и запуск Docker

Нужны работающий Docker и Docker Compose. Команды выполняются из корня проекта:

```sh
docker compose up -d --build
```

Команда собирает образы и запускает PostgreSQL и API в фоне. Данные сохраняются после перезапуска контейнеров.
При неудачном старте API автоматически перезапускается, пока PostgreSQL поднимается.

Посмотреть логи и остановить сервис:

```sh
docker compose logs -f
docker compose down
```

В WSL добавляйте `sudo` к командам Docker, если доступ без него не настроен.

## Что реализовано в API

- Создание, просмотр, изменение и удаление задач: `/api/v1/tasks`.
- Смена статуса задачи: `/api/v1/tasks/{task_id}/status`.
- Фильтры по исполнителю, проекту, статусу, просроченности и открытым задачам.
- Справочники проектов и сотрудников из БД: `/api/v1/projects`, `/api/v1/employees`.
- Проверка подключения к БД: `/health`.

## PostgreSQL

Сервис `database` содержит схему и демоданные. API подключается к нему через SQLAlchemy; подключение задаётся переменной `DATABASE_URL` в Compose. ID в API передаются строками, например `"1"`; актуальные ID проектов и сотрудников доступны в справочниках.

В БД номер задачи `tasks.number` назначается автоматически: `<Код проекта>-<Порядковый номер>`, например `API-1`. Счётчик отдельный для каждого проекта; удалённые номера не используются повторно. При переносе задачи в другой проект назначается новый номер. Новому проекту нужно задать уникальный `code`; после выдачи номеров менять его нельзя.

Срок задачи — календарная дата, затраченное время — минуты. Связи сохраняются в `task_links`; при удалении задачи ссылки на неё удаляются автоматически.

На новой БД SQL-скрипты выполняются автоматически. Для существующей БД сначала соберите образ:

```sh
docker compose up -d --build database
```

Примените только ещё не выполненные обновления, каждое один раз: `02` добавляет номера, `03` — поля и связи для API. Существующие сроки в `03` преобразуются в даты по часовому поясу Europe/Moscow.

```sh
docker compose exec database psql -U taskUser -d TaskBase -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/02_task_numbers.sql
docker compose exec database psql -U taskUser -d TaskBase -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/03_api_storage.sql
docker compose up -d --build database-api
```

При запуске Python без `DATABASE_URL` доступен прежний мок в памяти; при недоступности настроенной БД API возвращает ошибку и не переключается на мок.

## Swagger

Вся информация по API — методы, параметры, схемы запросов и ответов — доступна в Swagger.
После запуска откройте [http://localhost:8000/docs](http://localhost:8000/docs).
Чтобы вызвать метод, нажмите **Try it out** -> **Execute**.

## Работа с Git и CI/CD

Разработка ведётся по Gitflow. `main` содержит выпущенную версию, `develop` —
изменения для следующего релиза. Изменения в обе ветки вносятся через Pull Request
(PR). Для слияния используйте **Create a merge commit**. Прямые push в `main`
и `develop` должны блокироваться правилами защиты репозитория с обязательным PR
и успешной проверкой `API checks`.

| Ветка | Откуда создавать | Куда открывать PR |
| --- | --- | --- |
| `feature/*` | `develop` | `develop` |
| `release/*` | `develop` | `main`; исправления, сделанные при подготовке релиза, также вернуть в `develop` |
| `hotfix/*` | `main` | `main` и `develop` |

### Обычная разработка

Команды выполняются на рабочем компьютере из корня проекта. Начните задачу
с актуальной `develop`, например для изменения фильтров задач:

```sh
git fetch origin
git switch -c feature/task-filters origin/develop
```

После изменения файлов API сохраните их в коммит и отправьте ветку:

```sh
git add database-api
git commit -m "Update task filters"
git push -u origin feature/task-filters
```

На GitHub создайте PR с **base: develop** и **compare: feature/task-filters**.
При открытии PR запускается CI. Если проверка упала, исправьте код и отправьте
новый коммит в эту же ветку — проверки запустятся повторно. После успешной проверки
слейте PR в `develop`. Обновление `develop` также запускает CI.

### Выпуск релиза

Когда изменения в `develop` готовы к выпуску, создайте релизную ветку:

```sh
git fetch origin
git switch -c release/0.1.0 origin/develop
git push -u origin release/0.1.0
```

Создайте PR с **base: main** и **compare: release/0.1.0**. Исправления при подготовке
релиза коммитьте в эту ветку. После успешных проверок слейте PR в `main`.
Это автоматически запускает проверку итогового коммита, публикацию образа и,
если включено развёртывание, обновление приложения на сервере.

Если в релизной ветке появились исправления относительно `develop`, откройте
также PR из `release/0.1.0` в `develop`. Удаляйте релизную ветку после завершения
нужных слияний.

### Срочное исправление выпущенной версии

Создайте hotfix от актуальной `main`:

```sh
git fetch origin
git switch -c hotfix/health-check origin/main
```

Внесите исправление, создайте коммит и отправьте ветку командой
`git push -u origin hotfix/health-check`. Откройте PR из неё в `main` и дождитесь
успешных проверок. Слияние запустит тот же цикл публикации и развёртывания,
что и выпуск релиза. Затем слейте эту hotfix-ветку через отдельный PR в `develop`,
чтобы исправление вошло в следующие релизы. После обоих слияний ветку можно удалить.

### Когда запускаются проверки и развёртывание

Поведение задано в [workflow API CI/CD](.github/workflows/ci-cd.yml).

| Событие | Что выполняется |
| --- | --- |
| Push в `feature/*` без открытого PR | Workflow не запускается |
| Открытие, обновление, повторное открытие или редактирование PR в `develop` или `main` | `API checks`, включая проверку допустимого имени исходной ветки |
| Push в `develop`, `release/*` или `hotfix/*` | `API checks` |
| Обновление `main` после слияния PR | `API checks` → `Publish image to GHCR` → `Deploy to Minikube with Helm` при `DEPLOY_ENABLED=true` |
| Создание тега | Workflow не запускается |

Если у `release/*` или `hotfix/*` открыт PR, новый push может запустить две проверки —
для самой ветки и для её слияния с целевой веткой PR.

`API checks` проверяет Helm-чарт через `helm lint`, запускает pytest в Docker,
собирает образ API, запускает его и проверяет HTTP-ответ `/health`.
В PR дополнительно проверяется направление слияния: в `main` разрешены
`release/*` и `hotfix/*`, в `develop` — `feature/*`, `release/*` и `hotfix/*`.

После успешной проверки коммита в `main` job `Publish image to GHCR` публикует
тот же проверенный образ в `ghcr.io/sugarycone/astalavistaservice/database-api`
с меткой `sha-<полный SHA коммита>`. Публикация требует включённой защиты `main`.
Если проверки или публикация завершились ошибкой, следующие этапы не выполняются.

Job `Deploy to Minikube with Helm` выполняется после публикации, если переменная
репозитория `DEPLOY_ENABLED` равна `true`. Он использует настройки окружения
`production`, подключается к серверу по SSH и передаёт чарт из того же коммита.
Helm устанавливает или обновляет релиз `database-api` в контексте и namespace
`astalavista`. Образ выбирается по digest, то есть по точному идентификатору
опубликованного содержимого. Если в `main` уже появился более новый коммит,
этот запуск пропускает обновление сервера.

Helm ожидает готовности приложения по `/health` и откатывает неудачное обновление
благодаря `--atomic`. При пересоздании Pod данные мок-API в памяти сбрасываются.
Пока `DEPLOY_ENABLED` отсутствует или отличается от `true`, выполняются проверки
и публикация, а job развёртывания пропускается.

Результаты и логи смотрите в **GitHub → Actions → API CI/CD**. Первоначальная
настройка защиты веток, сервера, SSH и переменных описана в
[инструкции по развёртыванию](docs/deployment.md).
